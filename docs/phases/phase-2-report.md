**Status: implemented and verified, locally and in CI, with one gap: no live World Bank
retrieval could be run where Phase 2 was built** (the build environment's network policy
blocks the provider). Everything else — schema, provider layer, pipeline, quality rules,

plan written before implementation is in [phase-2-plan.md](phase-2-plan.md).

## 1. Phase 1 audit findings

Phase 1 was sound (CI green on its first run: 125 backend tests on SQLite and PostgreSQL,
117 frontend, 19 integration). Findings that shaped Phase 2:

- **Reusable as-is:** the app factory with injected settings, the error envelope and
  request IDs, pagination, portable enum columns, UTC datetimes, deterministic constraint
  names, batch migrations with drift tests, the OpenAPI snapshot → generated types, the
  cached resource hook and the component library.
- **Limitations to design around:** no authentication (so ingestion could not be an HTTP
  endpoint); SQLite's `NUMERIC` is binary floating point (so an exact-decimal type was
  needed); the network service assumed the newest dataset was the reference one (fixed by
  `datasets.kind`); `seed --reset` deletes by kind (so new foreign keys to Phase 1 entities
  use `SET NULL`).
- **Integration risk:** a World Bank *annual average* is not the Phase 1 *daily* or
  *monthly* variable of the same name — links between them state the difference.
- **Documentation debt:** Phase 1 docs named FRED as the Phase 2 source; the licence review
  overturned that (see section 4) and the docs were corrected.

## 2. Phase 2 architecture

```
command line ─► catalogue ─► provider (throttle · retries · typed errors) ─► capture bytes
            ─► parse (Decimal) ─► normalise ─► quality rules ─► revisions ─► store ─► job record
web client ─► read-only API ─► services ─► database ◄─────────────────────────────────┘
```

New backend package `app/ingestion/` (providers, HTTP, normalisation, quality, persistence,
jobs, two pipelines, catalogue, command line); new schemas, services and routes for the
read API; migration `0002`; frontend `features/data/` and four pages. No new dependency on
either side. Details: [data architecture](../data/architecture.md).

Key design choices: **capabilities, not a catch-all interface** (a provider implements only
what it can do); **one database transaction per series** (a failure never leaves half a
series); **job status derived from targets** (with `partially_failed`); **ingestion from
the command line only** until authentication exists.

## 4. Provider selection rationale

- **World Bank** — no key, a clear open licence permitting commercial use with
  attribution, good India coverage, stable documented API. Downsides accepted: mostly
  annual, publication lag, errors inside HTTP 200 responses (handled).
- **FRED — rejected.** Its API terms (June 2024) prohibit storing FRED content in a
  database; RUMIN stores data by design.
- **MoSPI — next.** The right source for official monthly Indian statistics, but it needs an
  access token; licence to confirm.
- **RBI DBIE** — no official API. **Alpha Vantage** — free tier non-commercial.
  **NSE/BSE** — licensed data, hence the price-file import instead of any bundled prices.

The terms were read through search results because the build environment could not open
provider sites; each licence must be re-read in full before commercial use.

## 5. Database schema

Migration `0002_financial_data_infrastructure` extends `datasets` (`kind`, provider,
licence URL, terms URL, attribution, update frequency, provider's last update, and a
CHECK that curated rows have a checksum and provider rows a provider) and adds nine tables:
`data_providers`, `economic_series`, `economic_observations`, `instruments`, `price_bars`,
`ingestion_jobs`, `ingestion_job_items`, `source_captures`, `data_quality_issues`.

- **Exact decimals:** `NUMERIC(38, 18)` on PostgreSQL, a canonical decimal string on
  SQLite; values that do not fit are refused, never rounded.
- **One current row per period** (and per instrument, dataset and trading day) enforced by
  partial unique indexes `WHERE superseded_at IS NULL`; revisions sit alongside.
- **Provenance foreign keys** (`RESTRICT`): a value cannot lose its job or capture.
- Indexes on every filter and join path. Downgrade tested (it removes provider datasets
  first).

Full description: [data model](../data-model.md) and [data dictionary](../data-dictionary.md).

## 6. Ingestion pipeline

For each series: validated request → throttle (≥ 1 s between requests) → HTTP with up to 4
attempts for temporary failures (backoff with jitter; `Retry-After` up to 60 s) → the exact
bytes stored (gzip, SHA-256) → JSON parsed with numbers as `Decimal` → strict
normalisation → quality rules → revision logic (new / unchanged / revised; `5.10` = `5.1`;
absent periods untouched) → stored in one transaction → summaries refreshed → job item
recorded. After three consecutive temporary failures the remaining series are skipped
(`circuit_open`) rather than hammering a provider that is down. Ctrl+C records the job as
`cancelled`; a crashed run is closed as abandoned by the next command.

Run it with `make catalog` and `make ingest`; inspect with `make ingest-jobs`. Exit codes
0 / 1 / 2 / 3 / 130 distinguish completed, failed, not started, partially failed and
cancelled. Details and troubleshooting: [ingestion](../data/ingestion.md).

## 7. Data quality framework

**Structural problems reject; plausibility problems flag; nothing is corrected.** 30 rules:
14 reject (e.g. `invalid_number`, `precision_exceeded`, `frequency_mismatch`,
`future_period`, `high_below_low`), 6 flag (e.g. `outside_review_range`,
`period_in_progress`, `large_price_move` > 40 %), 10 note (e.g. `missing_values`,
`provider_flag`, `unexpected_gap`, `trading_gap`). Rejected records are kept as issues
with exactly what the source sent; flagged values are stored as reported with quality
status `warning`. Review ranges are RUMIN's assumptions and are labelled so. The rules are
published by the API and documented in [data quality](../data/quality.md).

## 8. Data provenance approach

Every value carries: its provider and dataset (with licence, licence URL, attribution,
terms, the provider's last update), the series' full description (unit, frequency,
measure, basis, seasonal adjustment, currency, original source organisation), the
provider's literal, the job that first received it and the job that last confirmed it,
the capture it came from (sanitised URL or file name, time, HTTP status, SHA-256, the
bytes), its revision history, and its quality issues. **Freshness is three separate facts
— observation period, retrieval time, provider's last update — and never a score.**

## 9. API endpoints

Read-only, under `/api/v1`: `providers`, `providers/{id}`, `datasets`, `datasets/{id}`,
`economic-series` (filters, search, sort), `economic-series/{id}`,
`economic-series/{id}/observations` (date range, missing and revisions toggles),
`instruments`, `instruments/{id}`, `instruments/{id}/prices` (one dataset at a time —
sources are never blended), `ingestion-jobs`, `ingestion-jobs/{id}`,
`source-captures/{id}` (metadata only), `data-quality/issues`, `data-quality/rules`; and
`system` now reports stored data. Data values travel as exact decimal strings in plain
notation. There is deliberately no endpoint that starts ingestion. See [api.md](../api.md).

## 10. Frontend functionality

- **Data Explorer** (`/data`): stored-data figures; the series catalogue with coverage,
  latest value, last retrieval, search and filters; a notice that explains a failed
  retrieval (with counts, a link to the run and the command to retry); instruments; dataset
  cards with licence links and attribution; recent runs.
- **Series page:** honest labels (Observation, "Historical · not live", "Sample data — not
  real", flagged count), the three freshness facts, a notice when the last retrieval failed
  or was skipped, an accessible chart (gaps for missing periods, triangles for flagged
  values, crosshair tooltip with exact values, operable from the keyboard as a slider) with
  an exact-value table twin (published literals, revision history on request), source and
  licence, the review range labelled as an assumption, and the latest quality issues.
- **Instrument page:** close-price chart and OHLCV table per dataset, trading gaps left as
  gaps, provenance and quality issues.
- **Ingestion run page:** each target's outcome and error, stored responses with SHA-256,
  issue counts, run details.
- Overview and System pages report stored data and the new capabilities. Checked at desktop
  and phone widths, in both themes.

## 11. Security considerations

- Ingestion cannot be started over HTTP (no authentication yet); the API is read-only for
  data (`POST /api/v1/ingestion-jobs` → 405).
- Provider URLs are built only from validated parts; the base URL must be `https://`.
- Bounded work: response size (20 MB), pages (20), timeouts, retries, `Retry-After` cap,
  circuit breaker; price files ≤ 10 MB with a strict format.
- No secrets exist (the World Bank needs no key); credential-like query parameters are
  redacted before any URL is logged or stored; job messages never include bodies or stack
  traces; imported files are recorded by name only; stored bodies are never served.
- Strict validation of every path and query parameter; LIKE wildcards escaped; https-only
  links from validated manifests and the catalogue.
- No new dependencies; `npm audit` found no vulnerabilities; Python dependencies were not
  tool-audited.
- **Not production-secure:** no authentication, no inbound rate limiting, no security
  review. See [security.md](../security.md).

are single grouped queries.

## 14. Known limitations

The most important (full list: [known-limitations.md](../known-limitations.md)):

- **No live World Bank retrieval was verified** where Phase 2 was built; a person should
  run `make ingest` once with internet access and review the result.
- Provider terms were read through search results; re-read before commercial use.
- Annual data only, one provider; recent years usually unpublished.
- No price data unless imported; RUMIN cannot verify the licence a user declares; no
  corporate-action adjustments or currency conversion.
- Review ranges are assumptions; no review workflow (issues stay `unreviewed`).
- No authentication, no inbound rate limiting; local use only.

## 15. Unimplemented features

Deliberately not built in Phase 2: MoSPI and any keyed provider; real-time, intraday or
streaming data; scheduling; an HTTP ingestion trigger; a review workflow for issues;
corporate-action adjustment; currency conversion; financial statements and company data;
retention/pruning of stored bodies; charts in the Universe and Scenario Lab; anything from
later phases (graph analytics, simulation, AI analyst, 3D).

## 16. Recommended Phase 3 improvements

1. **First, verify a live World Bank run** and review the stored values, captures and
   issues; fix anything the real API does differently from its documentation.
2. **Knowledge graph on real data:** connect series to entities and variables as graph
   edges with their stated relations; expose "what data describes this node".
3. **MoSPI provider** for monthly official Indian statistics, with its key server-side.
4. **Issue review workflow** (reviewer, decision, note) — needed before data is used for
   analysis.
5. **Observation views in the Universe and Scenario Lab:** the latest related value next to
   a variable, with the difference in measure stated.
6. **Operational hygiene:** dependency and secret scanning in CI, `pip-audit`, a retention
   policy for stored bodies, and browser end-to-end tests for the data pages.
